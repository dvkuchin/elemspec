# ElemSpec — исполняемые UI-спецификации для 1С:Элемент

`elemspec` — самостоятельный инструмент для декларативных UI-тестов. Автор описывает
поведение веб-приложения русским Gherkin, а движок превращает фразы в фиксированные
действия Playwright, выполняет их в Chromium и создаёт JSON/HTML-отчёт.

Это не приложение 1С:Элемент, не библиотека внутри тестируемого приложения и не
генератор одноразового Playwright-кода. Это отдельный устанавливаемый Python-пакет с
языком тестов, CLI, MCP-сервером, навыком ИИ-автора и дорожной картой.
Wheel уже собирается; публикация в PyPI ещё не выполнена.

## Статус

- Текущая версия: **`0.5.0.dev0`**.
- Проект до первого стабильного релиза: интерфейсы и форматы можно менять без
  слоя обратной совместимости.
- Основная проверенная среда — macOS. Linux и Windows включены в CI-матрицу, но
  первый публичный прогон и чистый onboarding ещё не выполнены.
- Движок и проекты feature-тестов разделены: рабочие сценарии приложения не входят
  в репозиторий ElemSpec.

## Кому и зачем он нужен

| Роль | Цель | Как работает |
| --- | --- | --- |
| Тестировщик / тест-менеджер | описать бизнес-сценарий, принять покрытие | формулирует наблюдаемые ожидания, читает Gherkin и отчёт |
| Разработчик приложения | получить воспроизводимую регрессию | запускает тесты, читает первый красный шаг, снимок и видео |
| Автор feature-теста | создать исполнимый сценарий | пишет DSL вручную или вызывает `$new-test` |
| Разработчик elemspec | развивать DSL, движок, MCP и отчёты | меняет `src/`, схемы и контракты отдельно от сборки конкретного теста |
| ИИ-агент | перевести прозу в доказанный тест | уточняет только бизнес-решения, исследует DOM сам и работает через MCP |

Один человек может совмещать несколько ролей. Граница важна не для оргструктуры, а для
решений: требование к продукту подтверждает человек, локатор выясняет агент, а новую фразу DSL
реализуют отдельно в движке.

## Как устроен инструмент

```text
текст сценария
        │
        ▼
new_test + ИИ-клиент ─────────┐
        │                          │ только узкие команды
        ▼                          │
elemspec mcp → доверенное ядро ←┘
        │
        ├─ живая browser-разведка и evidence
        ├─ валидация, сессия, атомарная запись
        └─ prove: green → временный red → green
        │
        ▼
tests/<имя>/{init.json,test.feature}
        │
        ▼
elemspec: Gherkin → steps.py → actions.py → Playwright
        │
        ▼
_reports/<дата>/report.{json,html} + снимки/видео
```

Компоненты:

- `elemspec` — основной CLI-исполнитель;
- `src/elemspec/` — Python-пакет движка и агентского ядра;
- `elemspec mcp` — stdio MCP-транспорт доверенного агентского ядра;
- MCP prompt `new_test` — переносимая инструкция для поддерживающих prompts клиентов;
- `$CODEX_HOME/skills/new-test/` — дополнительная удобная оболочка для Codex;
- `elemspec mcp-config` — готовые параметры подключения из интерфейса ИИ-клиента;
- `elemspec integrate codex` — установка/проверка пользовательского skill и MCP;
- `elemspec author` — отдельный строгий Codex CLI без shell и произвольной записи;
- `elemspec.toml` — точный allowlist hostname для движка и browser-разведки;
- `tests/` — версионируемые тесты в независимом проекте пользователя;
- `_reports/` и `.elemspec/` — локальные артефакты проекта тестов, в Git не входят.

## Быстрый старт

Полная процедура — в [инструкции установки](https://github.com/dvkuchin/elemspec/blob/main/docs/installation.md). До публикации PyPI
из checkout:

```bash
pipx install .
elemspec install-browser
elemspec --version
elemspec mcp-config
elemspec --project examples/getting-started run smoke
```

## Запуск feature-тестов

```bash
elemspec run                                        # все тесты текущего проекта
elemspec run smoke                                  # один тест
elemspec run smoke checkout
elemspec list                                       # тесты и фразы DSL
elemspec run --headed                               # с окном Chromium
elemspec run --video --open                         # WebM и автооткрытие HTML
elemspec run --report <каталог>                     # свой каталог отчёта
elemspec --project <путь> run smoke                 # явный проект
```

Имя теста — это имя каталога `tests/<имя>/`. Без имён движок запускает все каталоги,
в которых есть `init.json`.

Коды возврата:

- `0` — все выбранные тесты прошли;
- `1` — есть `провал` или `сломан`;
- `2` — тесты не найдены или неверен вызов CLI.

Код `1` означает, что хотя бы одна спецификация не прошла; подробности находятся
в HTML-отчёте.

## Формат теста

```text
tests/<имя>/
├── init.json      # базовый URL, browser, timeout, параметры
└── test.feature  # # language: ru, Функция, Сценарии, шаги
```

Пример:

```gherkin
# language: ru
Функция: Минимальная проверка
  Сценарий: Главная открывается
    Дано я открываю страницу "/"
    Тогда на странице есть текст "Example Domain"
```

Полный словарь, локаторы и `init.json` — в [справочнике языка](https://github.com/dvkuchin/elemspec/blob/main/docs/language.md).

## Отчёты и статусы

По умолчанию отчёт лежит в `_reports/<дата-время>/`:

- `report.json` — машинный результат;
- `report.html` — самодостаточный отчёт;
- `артефакты/` — снимки падений, явные скриншоты и WebM-видео.

| Статус | Смысл | Кто разбирает |
| --- | --- | --- |
| `ок` | шаг/сценарий прошёл | никто |
| `провал` | наблюдаемое поведение не совпало с ожиданием | сначала разработчик приложения |
| `сломан` | тест не смог выразить/выполнить шаг | автор теста или разработчик elemspec |
| `пропущен` | тег/конфиг отключил тест или предыдущий шаг уже упал | автор теста |

Первый упавший шаг останавливает только свой сценарий; другие сценарии продолжаются.

## Запись и курсор

- `--видео` записывает WebM (VP8); `--видео провал` оставляет видео только для упавших.
- `--курсор авто|да|нет` управляет рисованной красной точкой и вспышкой клика.
- Системный ffmpeg не нужен; Playwright пишет WebM своим компонентом. GIF без отдельного ffmpeg
  не генерируется.

## ИИ-автор тестов

Основной переносимый интерфейс ИИ-автора — локальный stdio MCP. Получите готовую
конфигурацию и добавьте сервер `elemspec` через интерфейс своего ИИ-клиента:

```bash
elemspec mcp-config
# если клиент не передаёт рабочий каталог серверу:
elemspec --project /path/to/my-specs mcp-config
```

Клиент с поддержкой MCP prompts покажет команду `new_test`. В Claude Code она
вызывается как `/mcp__elemspec__new_test`; в клиенте без меню prompts достаточно
попросить агента использовать MCP `elemspec` для создания теста.

Для Codex доступен дополнительный пользовательский skill `$new-test`:

```bash
elemspec integrate codex
elemspec integrate codex --check
```

После этого откройте проект тестов как рабочий корень новой задачи и вызовите
`$new-test`. Для технически строгого режима отдельный Codex CLI запускается с
`read-only` sandbox и единственным пишущим каналом — `elemspec mcp`:

```bash
elemspec author check
elemspec author cli
elemspec author exec "Создай тест ..."
```

Навык `$new-test`:

1. получает машинный контракт DSL и allowlist hostname;
2. уточняет недостающее бизнес-требование;
3. исследует живой сайт и доказывает локаторы;
4. валидирует и атомарно записывает только выбранный тест;
5. регистрирует engine gap, если DSL не хватает;
6. выполняет `green → временный red → green` или фиксирует подтверждённый дефект.

Подробнее: [пользовательский процесс](https://github.com/dvkuchin/elemspec/blob/main/docs/usage.md)
и [строгий ИИ-автор](https://github.com/dvkuchin/elemspec/blob/main/docs/authoring.md).

## Текущие возможности

- русский Gherkin: функции, сценарии, предыстория, scenario outline и примеры;
- три вида локаторов: `data-testid`, текст и CSS;
- открытие страниц, ожидания, проверки текста/элемента/адреса/title/количества;
- клик, ввод, клавиша, popup-вкладка, скриншот;
- параметры и `init.json`, headless/видимый режим, видео и рисованный курсор;
- JSON/HTML-отчёты, снимок падения, разделение `провал` / `сломан`;
- allowlist hostname до и во время навигации;
- статическая валидация, agent sessions, browser evidence, engine-gap registry и prove-протокол;
- строгий Codex CLI с единственным MCP-сервером.
- универсальный MCP prompt `new_test` и генератор конфигурации для локальных ИИ-клиентов.

## Ограничения и дальнейшее развитие

Ближайшие направления:

1. поиск и восстановление незавершённых агентских сессий;
2. вторая ИИ-агентская среда и разделение runtime/authoring-зависимостей;
3. секреты и авторизованные browser-сессии;
4. сценарии форм, списков и обратимого изменения данных;
5. исследование Playwright Codegen/recorder как источника журнала действий;
6. Linux/WSL onboarding, CI и первый стабильный релиз с политикой совместимости.
