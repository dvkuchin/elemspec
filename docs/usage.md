# Как получить и принять UI-тест

Эта инструкция — для разработчика, тестировщика или тест-менеджера, который хочет
превратить сценарий на обычном языке в версионируемый feature-тест.

Вы не обязаны писать DSL. Ваша задача — определить наблюдаемое требование и принять
результат. ИИ-агент проходит сайт вживую, находит локаторы, собирает русский Gherkin и
доказывает, что тест умеет как проходить, так и краснеть.

Готовый тест выполняется без ИИ: `elemspec` читает файлы и детерминированно запускает
заранее известные действия.

## Быстрый старт для нового приложения

### 1. Установить ElemSpec один раз на компьютере

Выполните [инструкцию установки](installation.md), затем проверьте CLI и браузер:

```bash
elemspec --version
elemspec install-browser
```

Команда `elemspec` после этого доступна из любого каталога. Пользователю движка не
нужно создавать или активировать `.venv`: изолированным Python-окружением управляет
`pipx`.

### 2. Получить адрес развёрнутого приложения

ElemSpec работает с сайтом, поэтому ему нужен URL тестового экземпляра, например:

```text
https://democrm.example.com/app
```

UUID приложения 1С:Элемент сам по себе URL не заменяет. Из URL отдельно выделите
hostname — имя хоста без `https://`, пути и порта:

```text
democrm.example.com
```

Этот hostname попадёт в allowlist проекта. Движок и ИИ-автор не смогут открыть
случайный сайт за его пределами.

### 3. Создать отдельный проект feature-тестов

Движок ElemSpec и тесты приложения — разные проекты. Для нового приложения создайте
отдельный каталог или Git-репозиторий:

```bash
mkdir democrm-specs
cd democrm-specs
elemspec init . --name DemoCRM --host democrm.example.com
```

Если каталог уже создан, достаточно перейти в него и выполнить последнюю команду.
Будет создана такая структура:

```text
democrm-specs/
├── elemspec.toml
├── tests/
├── engine-gaps/schema.json
├── БЭКЛОГ.md
└── .gitignore
```

В `elemspec.toml` хранится конфигурация проекта и список разрешённых хостов;
в `tests/` — исполняемые feature-тесты; в `engine-gaps/` — запросы на недостающие
возможности языка.

Проверьте созданный проект:

```bash
elemspec doctor
elemspec list
```

До появления первого теста пустой список — нормальное состояние.

### 4. Подключить ElemSpec к Codex один раз

После установки или обновления движка выполните из любого каталога:

```bash
elemspec integrate codex
elemspec integrate codex --check
```

Команда устанавливает пользовательский `$new-test` и регистрирует глобальный stdio
MCP `elemspec` штатной командой Codex. Создайте новую задачу после установки: уже
открытая задача не пересобирает список навыков и MCP-инструментов.

### 5. Запустить ИИ-автора в обычной задаче

Откройте именно каталог `democrm-specs` как рабочий корень Codex, а не его родительский
каталог. Это нужно и для обнаружения `elemspec.toml`, и для выбора правильного проекта
глобальным MCP-сервером.

В новой обычной задаче напишите:

```text
Используй $new-test.

Создай тест для https://democrm.example.com/app:
1. Открыть приложение.
2. Перейти в список клиентов.
3. Убедиться, что виден заголовок «Клиенты».
```

Имя навыка в тексте — `$new-test`. Это не slash-команда `/new-test`, поэтому она не
обязана появляться в меню после ввода `/`; проверить обнаружение можно через `/skills`.

Обычная задача — удобный режим. Skill требует использовать только MCP ElemSpec, но
остальные инструменты задачи технически не отключены.

### 6. При необходимости запустить строгого автора

Находясь в каталоге проекта тестов, выполните:

```bash
elemspec author check
elemspec author cli
```

`author cli` открывает отдельную задачу Codex с жёстким контуром ElemSpec: подключает
навык, разрешает только доверенный MCP движка и запрещает агенту обходить его через
shell или произвольный браузер. В открывшейся задаче напишите обычным текстом:

```text
Используй $new-test.

Создай тест для https://democrm.example.com/app:
1. Открыть приложение.
2. Перейти в список клиентов.
3. Убедиться, что виден заголовок «Клиенты».
```

Для одной неинтерактивной задачи можно использовать:

```bash
elemspec author exec 'Используй $new-test. Создай тест ...'
```

Одинарные кавычки не дают Bash трактовать `$new-test` как shell-переменную.

### 7. Запустить готовые тесты

ИИ для выполнения уже созданных feature-файлов не нужен:

```bash
elemspec run                           # все тесты проекта
elemspec run smoke                     # выбранный тест tests/smoke
elemspec run --headed                  # все тесты в видимом браузере
elemspec run --video провал --open     # видео падений и открытие HTML-отчёта
```

Команды можно запускать не из корня проекта, если явно передать его путь:

```bash
elemspec --project /path/to/democrm-specs run
```

### Частые ошибки первого запуска

- `elemspec: command not found` — ElemSpec ещё не установлен через `pipx` либо
  терминал не был перезапущен после `pipx ensurepath`. Вернитесь к
  [инструкции установки](installation.md).
- `не найден elemspec.toml` — команда запущена до `elemspec init` или не из каталога
  проекта тестов. Перейдите в нужный каталог либо добавьте
  `--project /path/to/project` перед подкомандой.
- `Chromium: не найден` — выполните `elemspec install-browser`, затем повторите
  `elemspec doctor`.
- `$new-test` отсутствует в `/skills` — выполните `elemspec integrate codex --check`
  и после успешной проверки создайте новую задачу над корнем проекта тестов.
- MCP `elemspec` сообщает, что проект не найден — рабочим корнем задачи выбран не
  каталог с `elemspec.toml`. Откройте проект спецификаций как отдельный рабочий корень.

## Роли и зоны ответственности

### Автор требования

- говорит, что и при каком исходном состоянии нужно проверить;
- определяет, что считается успехом;
- решает, является ли найденное расхождение дефектом;
- принимает покрытие, Gherkin и технический долг.

### ИИ-агент `$new-test`

- проверяет allowlist hostname;
- задаёт вопросы только о недостающем бизнес-решении;
- сам выясняет DOM, локаторы, ожидания и фактические переходы;
- пишет только через доверенное MCP-ядро;
- не расширяет DSL походу, а формирует engine gap;
- возвращает машинно подтверждённый статус.

### Автор DSL / разработчик elemspec

Отдельно реализует недостающую Gherkin-фразу, её семантику и тесты. Сборка конкретного
сценария не даёт агенту права менять `src/`.

## Как сформулировать наблюдаемый сценарий

Хорошо:

> Открыть главную test.example.com. В шапке нажать «Тарифы». Должен открыться
> раздел тарифов, показаться заголовок «Тарифы» и кнопка выбора.

Плохо:

> Проверить, что портал работает корректно.

Каждый пункт должен отвечать на вопрос: «что пользователь сделает и что он после этого увидит?»

Желательно указать:

- начальный URL;
- исходное состояние и данные;
- действия;
- ожидаемые видимые результаты;
- какие изменения данных допустимы;
- должен ли тест убрать созданные данные;
- какое имя каталога теста нужно, если оно важно.

Локаторы, `data-testid`, CSS и таймауты указывать не нужно: это техническая разведка агента.

## Как заказать тест у строгого автора

```bash
cd /path/to/democrm-specs
elemspec author cli
```

В открывшемся Codex CLI можно явно вызвать навык:

```text
Используй $new-test.

Сайт: https://test.example.com
Имя теста: тарифы

Сценарий:
1. Открыть главную.
2. Нажать «Тарифы».
3. Должны появиться заголовок «Тарифы» и кнопка выбора.

Данные: не нужны.
Изменение данных: не допускается.
```

## Как отвечать на вопросы агента

Нормальные вопросы:

- что именно считать успехом;
- какой объект выбрать, если в сценарии их несколько;
- можно ли добавить hostname в allowlist;
- является ли расхождение дефектом;
- можно ли изменить существующий тест по показанному diff.

Ненормальные вопросы в этом процессе:

- «какой CSS взять?»;
- «какой `data-testid` у кнопки?»;
- «сколько миллисекунд ждать?».

Это агент должен выяснить живой разведкой. Если агент просит дать ему shell, прямую запись или
посторонний browser, это обход строгого контура; не разрешайте.

## Что делает ядро

Обычный путь:

```text
INTAKE → DISCOVERY → VALIDATED → APPLIED → COMPLETE
```

Ключевые гарантии:

- сайт открывается только при точном совпадении hostname с `elemspec.toml`;
- локаторы подтверждаются журналом browser evidence;
- новый тест записывается только после валидации и evidence;
- изменение существующего теста ждёт подтверждения diff и его ревизии;
- `prove` меняет только временную копию и восстанавливает рабочий тест;
- найденный дефект не прячется ретраями и требует решения автора.

## Как принять результат

Итоговые статусы агентского контура:

| Статус | Что он доказывает | Что делать автору |
| --- | --- | --- |
| `COMPLETE` | исходный green, искусственный red со снимком, финальный green | прочитать feature и принять смысл проверки |
| `COMPLETE_WITH_GAPS` | исполнимая часть доказана, но часть требований связана с engine gaps | решить, нужно ли развивать DSL |
| `BUG_CONFIRMED` | тест воспроизводит явно подтверждённый дефект на том же шаге | завести/связать дефект; не называть тест зелёным |

Чек-лист приёмки:

1. Каждое исходное требование либо покрыто, либо связано с gap?
2. Проверяется наблюдаемый факт, а не случайная деталь текущей вёрстки?
3. Для «пользователь видит» использовано `виден`, а не просто `есть`?
4. Локаторы устойчивы? `data-testid` лучше текста, CSS — технический долг.
5. Не зафиксировано лишнее количество/порядок, которого нет в требовании?
6. Есть ли ссылки на feature, `init.json`, отчёт и снимок red/дефекта?

## Как повторно запустить тесты

```bash
elemspec run smoke
elemspec run smoke --headed
elemspec run smoke --video --open
elemspec run                           # все тесты
```

Код `1` означает реальное несовпадение или поломку сценария. Смотрите конкретный
первый упавший шаг и HTML-отчёт проекта тестов.

## Ручной режим

Тест можно написать вручную: создать `tests/<имя>/init.json` и `test.feature` по
[справочнику языка](language.md).
Ручной режим не освобождает от обязательных шагов:

1. пройти сценарий вживую;
2. проверить уникальность локаторов;
3. прогнать исходный green;
4. временно изменить проверку, получить red со снимком;
5. вернуть исходник и ещё раз получить green.

При `$new-test` этот prove-протокол делает ядро в изолированной копии; ручная правка рабочего feature
не нужна.

## Когда идти к разработчику приложения

Основной локатор — осмысленный уникальный `data-testid`. Если компонент имеет автоимя
`Надпись6`, имя дублируется или атрибута нет, агент может временно взять текст/CSS и зафиксирует долг.

Пример задачи:

> В подвале блок «Отдел продаж» не имеет уникального имени компонента. Задать ему
> осмысленный уникальный `data-testid`, например `НадписьОтделПродаж`, и синхронно обновить тест.

Имя компонента — контракт. Его переименование может сломать тесты и должно быть согласовано.
