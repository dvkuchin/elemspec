# Язык тестов ElemSpec

Справочник языка - держать под рукой, когда пишешь тест. Тесты пишутся
на **Gherkin** (язык сценариев Cucumber) по-русски, в файле `test.feature`;
рядом лежит `init.json` с окружением и параметрами - оба описаны здесь.

Для первого знакомства лучше [пользовательская инструкция](usage.md); установка с нуля —
[installation.md](installation.md); обзор движка, запуск и отчёты — [README](../README.md).

## test.feature

```gherkin
# language: ru
Функция: Тестовый портал — корзина
  Свободный текст под заголовком - описание: что и зачем проверяем.
  Попадает в отчёт.

  Предыстория:
    Дано я открываю страницу "/"
    И я жду элемент "ШапкаСайта"

  Сценарий: Пустая корзина
    Когда я нажимаю "КнопкаКорзина"
    Тогда виден элемент "ГруппаПустаяКорзина"

  @пропустить
  Сценарий: Ещё не готов
    Тогда на странице есть текст "..."
```

Строение:

- `# language: ru` - первая строка, обязательна: включает русские ключевые слова.
- **Функция** - одна на файл: имя теста и описание.
- **Сценарий** - их может быть несколько. Каждый сценарий - **отдельная единица
  прогона**: свой чистый браузерный контекст (пустые куки, хранилище, корзина),
  своя строка в отчёте «Функция › Сценарий», свои снимки и запись.
- **Предыстория** - общие шаги, выполняются заново **перед каждым** сценарием
  файла. Место для «открыть и дождаться» и, в будущем, для входа в приложение.
- **Шаг** - строка `Ключевое слово + фраза`. Первый упавший шаг останавливает
  свой сценарий (дальше проверять нечего), остальные шаги помечаются «пропущен».
  Другие сценарии файла выполняются независимо.
- `#` в начале строки - комментарий. Хорошим тоном - помечать комментарием
  технический долг (селекторы, автоимена) и неочевидные решения.

### Ключевые слова

`Дано` (исходное состояние), `Когда` (действие пользователя), `Тогда` (ожидаемый
результат), `И` (продолжение предыдущего). Синонимы: `Допустим`, `Пусть`, `Если`,
`Затем`, `То`, `*`.

Движок ключевые слова **не различает** - смысл шага несёт фраза. Слова нужны
человеку: по ним сценарий читается как история. Соглашение обычное для Gherkin:
`Дано` - подготовка, `Когда` - действие, `Тогда` - проверка.

### Структура сценария: прогон по таблице

Один сценарий, выполненный для каждой строки таблицы. `<колонка>` в шагах
заменяется значением:

```gherkin
  Структура сценария: Разделы открываются из шапки
    Когда я нажимаю "<пункт>"
    Тогда адрес содержит "<адрес>"

    Примеры:
      | пункт  | адрес          |
      | Цены   | ?state=price   |
      | Журнал | ?state=journal |
```

В отчёте каждая строка - отдельный сценарий:
`Разделы открываются из шапки [пункт=Цены, адрес=?state=price]`.

### Теги

`@пропустить` над функцией или сценарием - статус «пропущен», не выполняется.
Других тегов движок пока не интерпретирует (писать можно, они игнорируются).

### Подстановки

`${имя}` **внутри кавычек** шага заменяется значением из `параметры` init.json
(вне кавычек не работает - фраза перестанет распознаваться):

```gherkin
    Тогда на странице есть текст "${телефон_отдела_продаж}"
```

Что выносить в параметры: значения, которые меняются по бизнес-причинам
(телефон, название тарифа), данные окружения (логин) и **длинные CSS-селекторы** -
под осмысленным именем селектор в фиче не режет глаз, а чинится в одном месте.

## Как указать элемент на странице

Половина шагов - «я нажимаю ...», «виден ...», «я ввожу ... в ...» - должна
понять, **о каком элементе страницы речь**. Для этого внутри шага пишется одно
из пяти общих указаний (в таблице шагов ниже это место обозначено `<лок>`).
Платформенные команды имеют отдельную семантическую форму:

```gherkin
    Когда я нажимаю "КнопкаВойти"                          # по имени компонента
    Когда я ввожу "TestUser" в поле "login-edit"      # input внутри компонента
    Когда я нажимаю пункт навигации "Sales"                # компонент Элемента по label
    Когда я нажимаю команду "Готово"                      # button по вложенной label
    Когда я нажимаю текст "Войти"                          # по видимой надписи
    Когда я нажимаю селектор "[data-component='badge']"    # по CSS-селектору
```

**По имени компонента** - основной способ. Разработчик приложения называет
компонент в исходниках, веб-клиент Элемента выводит имя на страницу (атрибут
`data-testid`), тест за него цепляется. Не ломается ни от смены надписи, ни от
правок вёрстки. Слово `элемент` можно писать и явно: `элемент "КнопкаВойти"` -
то же самое. При ручном исследовании имя видно в DevTools браузера
(правой кнопкой → Просмотреть код → `data-testid="..."`); ИИ-автор определяет
и проверяет его самостоятельно.

**Пункт навигации** - устойчивый платформенный локатор для меню 1С:Элемент.
Движок находит ближайший `data-component="navigation-item"` по точному тексту
вложенного `data-component="label"`. Текст такой метки является контрактом меню,
а совпадение обязано быть единственным. Карточка или заголовок с тем же текстом
не создают неоднозначность, потому что поиск ограничен компонентами навигации.

**Команда** - платформенная кнопка `data-component="button"`, найденная по
точному тексту вложенной `data-component="label"`. Она не смешивается с обычной
надписью того же текста и обязана быть уникальной.

**Поле именованного компонента** - устойчивый локатор для случая, когда
вложенные `input` имеют одинаковый служебный `data-testid`. В `поле "login-edit"`
значение - `data-testid` внешнего компонента, внутри которого должен быть
ровно один текстовый `input`, `textarea` или `[contenteditable="true"]`.

**По тексту** - когда имени у компонента нет. Работает, пока формулировку не
поменяли: надпись «Войти» - собственность маркетолога, а не тестов.

**По селектору** - крайний случай и технический долг: CSS поедет от первой же
правки формы. Выносите селектор в `параметры` init.json под осмысленным именем
и заводите разработчику задачу назвать компонент.

О чём стоит знать:

- **Имя есть не у всего.** Безымянным компонентам платформа выдаёт автоимя
  (`Надпись6`, `Группа1`), и автоимена повторяются по странице - опираться
  на них нельзя, это то же самое, что «первый попавшийся».
- **Имя - контракт.** Переименовали компонент в исходниках - сломали тесты.
  Та же дисциплина, что с `Ид`.
- **Имя может расходиться с надписью**: кнопка `КнопкаВКорзину` подписана
  «Купить». Это не ошибка - и лишний довод цепляться за имя, а не за текст.
- **Шаги-действия попадают ровно в один элемент.** Если совпадений несколько,
  `я нажимаю` и `я ввожу` честно ломаются и называют их число - клик «по первому
  из двенадцати» сделал бы тест зелёным не по той причине. Выход - уникальное
  имя или селектор с якорем (`:has(...)`, `:text-is(...)`).

## Стандартные шаги

`<лок>` - указание на элемент из предыдущего раздела: `элемент "X"`, `поле "X"`,
`пункт навигации "X"`, `текст "X"`, `селектор "X"` или голое `"X"`
(= `элемент`). Регистр букв не важен.
Этот же список из терминала: `elemspec list`.

| Текст шага | Описание |
| --- | --- |
| `я открываю страницу "/путь"` | Открывает адрес и ждёт загрузки (`load`). Относительный путь клеится к `базовый_адрес` из init.json, можно и полный `https://...`. HTTP 400+ - провал |
| `я жду <лок>` | Ждёт появления (видимости) элемента. Ставить после переходов и действий, запускающих перерисовку |
| `я жду N мс` | Пауза. Последнее средство - почти всегда правильнее `я жду <лок>` |
| `на странице есть текст "..."` | Ждёт и проверяет текст по всей странице. Пробелы/переносы/NBSP схлопываются - фразу, разбитую вёрсткой, можно писать одной строкой |
| `на странице нет текста "..."` | Проверяет отсутствие текста. Не ждёт - смотрит текущее состояние |
| `виден <лок>` | Элемент существует и реально отрисован. Ждёт появления |
| `есть <лок>` | Элемент существует в разметке - **может быть скрыт**. Для «пользователь видит» берите `виден` |
| `<лок> отсутствует` | Элемента нет. Ждёт исчезновения - на здоровом приложении мгновенна; если элемент есть, ждёт до таймаута и проваливается |
| `<лок> виден ровно N раз` | Счёт видимых элементов |
| `<лок> встречается ровно N раз` | Счёт по разметке (включая скрытые) |
| `адрес содержит "..."` | Вхождение в текущий URL |
| `заголовок вкладки содержит "..."` | Заголовок вкладки браузера (title) |
| `я нажимаю <лок>` | Клик. Требует ровно одного совпадения локатора |
| `я нажимаю команду "Готово"` | Нажимает уникальную платформенную команду по точной метке |
| `видна команда "Готово"` | Проверяет видимость уникальной платформенной команды |
| `я навожу указатель на <лок>` | Наводит указатель мыши. Требует ровно одного совпадения; использовать для меню, раскрывающегося по hover |
| `клик по <лок> открывает вкладку с адресом "..."` | Клик, открывающий новую вкладку (соцсети в подвале): проверяет адрес, который запросила вкладка, и закрывает её. Сверяется **первый** запрос - куда ведёт приложение; редиректы внешних сайтов (consent.youtube.com) не мешают. Вкладка не открылась или адрес не тот - провал |
| `я ввожу "значение" в <лок>` | Очищает поле и вводит значение. Ровно одно совпадение |
| `я очищаю поле "Имя"` | Очищает единственный редактор внутри именованного компонента поля |
| `я выбираю "Москва" в поле "БизнесРегион"` | Открывает платформенный выпадающий список поля, выбирает единственную строку с точным значением и проверяет результат |
| `поле "Имя" имеет значение "значение"` | Ждёт и проверяет точное пользовательское значение поля |
| `поле "Имя" пусто` | Ждёт и проверяет пустое пользовательское значение поля |
| `в таблице "Таблица" есть строка, где колонка "Колонка" имеет значение "Значение"` | Ждёт строку именованной платформенной таблицы с точным значением колонки |
| `в таблице "Таблица" нет строки, где колонка "Колонка" имеет значение "Значение"` | Ждёт отсутствия такой строки; подходит для проверки удаления или фильтрации |
| `я нажимаю клавишу "Enter"` | Клавиша: `Enter`, `Escape`, `Tab`, `ArrowDown`... (имена Playwright) |
| `снимок экрана "имя"` | Скриншот всей страницы в отчёт. При падении шага снимок делается сам - явный нужен для фиксации хорошего состояния |

Тонкости, о которые спотыкаются:

- **Ожидания «страница затихла» (networkidle) в языке нет намеренно**: на Элементе
  сеть не затихает никогда. Ждите конкретное - элемент или текст.
- **После клика с навигацией сначала ждите содержимое, потом адрес**: переход
  асинхронный, `адрес содержит` сразу после `я нажимаю` обгоняет навигацию.

  ```gherkin
      Когда я нажимаю "КнопкаКорзина"
      Тогда я жду элемент "ГруппаОформлениеЗаказа"
      И адрес содержит "?state=cart"
  ```

- **Проверка «стало не так, как было» начинается с фиксации начального состояния**:

  ```gherkin
      И селектор "${бейдж_корзины}" отсутствует
      Когда я нажимаю селектор "${кнопка_купить}"
      Тогда селектор "${бейдж_корзины_с_единицей}" виден ровно 1 раз
  ```

- **Количество - только там, где оно требование**: «кнопок покупки ровно 12»
  покраснеет от тринадцатого тарифа на здоровом портале.
- **Enter в выпадающих списках Элемента отменяет ввод** - выбирайте вариант кликом.

## init.json

```json
{
  "имя": "Тестовый портал: корзина",
  "базовый_адрес": "https://test.example.com",
  "таймаут_мс": 30000,
  "пропустить": false,
  "браузер": {
    "тип": "chromium",
    "headless": true,
    "вьюпорт": { "ширина": 1440, "высота": 900 },
    "замедление_мс": 0
  },
  "запись": "провал",
  "курсор": "авто",
  "параметры": {
    "приложение": "ЭДО",
    "бейдж_корзины": "[data-testid=\"ГруппаКорзина\"] [data-component=\"badge\"]"
  }
}
```

Обязательных полей нет, у всего есть умолчания:

| Поле | Умолчание | Смысл |
| --- | --- | --- |
| `имя` | имя каталога | как тест зовётся в отчёте |
| `базовый_адрес` | - | к нему клеятся относительные адреса из `я открываю страницу` |
| `файл_теста` | `test.feature` | можно указать другой файл |
| `таймаут_мс` | `30000` | предел всех ожиданий (элементов, текста, действий) |
| `пропустить` | `false` | `true` - тест не выполняется, статус «пропущен» |
| `браузер.тип` | `chromium` | также `firefox`, `webkit` (нужен `playwright install <тип>`) |
| `браузер.headless` | `true` | `false` - с окном (то же, что ключ `--видимый`) |
| `браузер.вьюпорт` | `1440×900` | размер окна |
| `браузер.замедление_мс` | `0` | пауза между действиями Playwright - разглядывать глазами |
| `запись` | `нет` | видео прогона: `всегда` / `провал` / `нет`, см. README |
| `курсор` | `авто` | рисованный курсор на записи: `авто` / `да` / `нет`, см. README |
| `параметры` | `{}` | значения для `${подстановок}` в шагах |

Ключи командной строки (`--видео`, `--курсор`) перекрывают init.json.
**Секретам в init.json не место** - это исходники под git.

## Статусы

| Статус | Смысл | Кто чинит |
| --- | --- | --- |
| `ок` | шаг/сценарий прошёл | - |
| `провал` | проверка не выполнилась: текста нет, элемента нет, HTTP 400+. **Приложение не такое** | разработчик приложения |
| `сломан` | нераспознанная фраза, битый Gherkin, неоднозначный локатор, таймаут действия. **Тест не такой** | автор теста |
| `пропущен` | `@пропустить`, `"пропустить": true` или шаг после падения | - |

Нераспознанная фраза ломает тест **до запуска браузера** - с файлом, строкой
и списком известных фраз.

## Особенности приложений 1С:Элемент, влияющие на тесты

- **Разделы - состояния одной страницы.** Клик по пункту шапки меняет адрес
  (`?state=price`) и **выкидывает содержимое предыдущего раздела из DOM**.
  Проверки раздела ставьте до перехода из него.
- **Скрытое остаётся в разметке** (обратный случай): «есть» не значит «видно»,
  для пользовательских проверок - `виден`.
- **networkidle не наступает** - платформа держит постоянное соединение.
  Фразы для него в языке нет; ждите элементы и тексты.
- **Синтетический `click()` из JS игнорируется** - навигация только по настоящему
  клику мыши. Учитывайте, исследуя страницу из консоли DevTools.
- **Модальные окна перехватывают клики** — закрывайте их шагом теста, иначе
  следующие действия могут попасть в перекрывающий слой.
- В выпадающих списках-справочниках клик по варианту проходит только после
  исчезновения «Идет поиск...», иначе значение молча теряется (память платформы,
  demoCRM).

## Хорошие практики

- **Тест должен уметь краснеть.** Написали - сломайте проверку намеренно,
  убедитесь в провале, верните. Правило без исключений.
- **Обратимость на живых сайтах.** Тест, меняющий состояние (корзина, записи),
  последними шагами убирает за собой и подтверждает уборку отдельной проверкой.
- **Один сценарий - один связный путь пользователя.** Независимые проверки -
  отдельные сценарии: у каждого чистый браузер, и падение одного не прячет
  результаты остальных.
- **Проверяйте требование, а не текущее положение дел** - иначе тест краснеет
  от развития продукта.
- **Не фиксируйте порядок там, где он не обещан**: «купить у второй карточки» -
  плохо (порядок товаров - не требование), «купить у карточки ЭДО» - хорошо.

## Ограничения (сейчас)

- Таблицы данных у шага (DataTable) и докстроки Gherkin не поддерживаются -
  парсер их поймёт, движок проигнорирует.
- Тегов-фильтров прогона нет (`@медленный` написать можно, отфильтровать - нет).
- «Мягких» шагов (провал не останавливает сценарий) нет.
- Своих фраз без правки движка не завести: словарь - `src/elemspec/steps.py`,
  как расширять - README, раздел «Новая фраза или действие».
