# Архитектура и состояние разработки ИИ-автора

Документ фиксирует границы, принятые решения и состояние реализации агентского
контура. Ближайшие публичные задачи перечислены в [ROADMAP](../ROADMAP.md).

## Статус продукта и совместимость

До первого опубликованного релиза проект находится в активной разработке:

- обратную совместимость CLI, Python API, JSON-схем и файлов внутреннего состояния
  не поддерживаем;
- при улучшении дизайна меняем существующий код напрямую, без адаптеров,
  deprecated-интерфейсов и миграционных прослоек;
- тесты и документация всегда описывают только текущий целевой интерфейс;
- обязательства по совместимости начнутся после отдельно принятого решения
  «релиз готов» и публикации первой стабильной версии.

Движок версионируется по совместимому с PyPI формату PEP 440. До стабильного релиза
используем версии вида `0.x.y.devN`. Текущая версия имеет единственный источник
в `src/elemspec/version.py`, показывается CLI и входит в JSON/MCP-контракт.
Релизная версия фиксируется git-тегом `v<версия>`.

Текущий срез: `0.6.0.dev0`; реализованы движок, доверенное ядро, JSON CLI, stdio MCP,
skill `$new-test`, browser evidence, prove-протокол и строгий Codex CLI. Ближайшая фаза — не переписывание
этого контура, а его переносимость, восстановление сессий, авторизация и расширение покрытия.

## Название и граница продукта

- Публичное имя продукта, Python distribution, import package и CLI: **ElemSpec / `elemspec`**.
- ElemSpec — отдельный устанавливаемый движок; он не должен искать тесты рядом со своим
  установленным Python-кодом.
- Каждый набор feature-тестов — независимый проект с собственным `elemspec.toml`, `tests/`,
  allowlist хостов и локальными отчётами.
- Playwright и конкретный ИИ-провайдер являются сменяемыми деталями реализации и не входят
  в название продукта.
- До первого стабильного релиза устаревшие имена и интерфейсы удаляются без
  слоя совместимости.

## Цель

Автор описывает UI-сценарий на произвольном человеческом языке. ИИ-агент:

1. выделяет предусловия, действия и наблюдаемые результаты;
2. определяет, достаточно ли требований и разрешений;
3. при необходимости задаёт уточняющие вопросы;
4. исследует приложение живым браузером и проверяет локаторы;
5. переводит сценарий в русский Gherkin из языка elemspec;
6. при нехватке языка не меняет движок, а формирует ТЗ на новый шаг;
7. валидирует и запускает тест;
8. доказывает, что проверка умеет краснеть;
9. возвращает файлы теста и отчёт о принятых решениях.

## Архитектура

### Слой 1. Skill: диалог и оркестрация

Skill понимает пользовательское намерение, классифицирует недостающие сведения,
задаёт вопросы и управляет процессом. Он не является границей безопасности:
инструкцию модель теоретически может нарушить.

### Слой 2. Доверенное локальное ядро

Ядро предоставляет узкие операции вместо произвольной работы с файлами:

- машинный контракт языка;
- чтение и валидацию тестов;
- создание и изменение только выбранного теста;
- проверку локаторов;
- запуск теста;
- атомарное доказательство красного с гарантированным восстановлением;
- регистрацию структурированного ТЗ на недостающий шаг.

Операции принимают имя теста, а не произвольный путь. Все пути проверяются
относительно `tests/`.

Доменная логика не зависит от транспорта. Она доступна внутреннему JSON API и
через публичную команду `elemspec mcp`.

### Слой 3. MCP-сервер

MCP публикует операции ядра разным ИИ-агентам. Для строгого ограничения агент
должен запускаться с доступом только к этому MCP и разрешённому браузерному API,
без свободной записи в репозиторий и без произвольного shell.

### Слой 4. elemspec

Существующий детерминированный исполнитель остаётся нижним уровнем:

`Gherkin → steps.py → actions.py → Playwright → JSON/HTML-отчёт`.

ИИ не генерирует одноразовый Playwright-код, а выбирает фразы фиксированного DSL.

### Граница тестового окружения

Считаем, что проект запускается только против контролируемых тестовых окружений,
поэтому отдельной классификации опасных кликов и токенов разрешения не вводим.
Вместо этого проект содержит обязательный `elemspec.toml` с точным allowlist
hostname. Ограничение действует и в обычном движке, и в агентской разведке:

- базовый адрес и абсолютные URL шагов проверяются до запуска;
- каждый верхнеуровневый переход и новая вкладка проверяются во время выполнения;
- поддомены не разрешаются автоматически;
- порт может быть любым — границей является hostname;
- запросы страницы к API/CDN не блокируются, если они не являются
  верхнеуровневой навигацией.

## Состояния процесса

- `INTAKE` — исходный текст разобран.
- `NEEDS_CLARIFICATION` — не хватает бизнес-требования.
- `READY_FOR_DISCOVERY` — требований достаточно.
- `DISCOVERY` — идёт живое исследование приложения.
- `LANGUAGE_GAP` — действие нельзя выразить текущим DSL.
- `DRAFT_READY` — подготовлены `init.json` и `test.feature`.
- `VALIDATED` — Gherkin и все фразы прошли статическую проверку.
- `UNVERIFIED` — для шага нет связанного browser evidence.
- `BUG_FOUND` — фактическое поведение расходится с требованием и ждёт решения
  автора.
- `APPLIED` — валидированный черновик атомарно записан в выбранный тест.
- `COMPLETE` — файлы восстановлены, итоговый тест зелёный, отчёт готов.
- `COMPLETE_WITH_GAPS` — исполнимая часть доказана, а каждое непокрытое
  требование связано с зарегистрированным `engine-gap`.
- `BUG_CONFIRMED` — автор подтвердил расхождение как дефект, а исходный прогон
  красный именно на этом шаге и содержит снимок.

Переходы между состояниями должны подтверждаться результатом операции ядра,
а не только утверждением модели.

## Классы вопросов

1. **Бизнес-уточнение.** Непонятно, какой наблюдаемый результат является
   требованием. Решение принимает автор.
2. **Граница окружения.** Нужный hostname отсутствует в allowlist проекта.
   Агент не открывает его и просит автора решить, является ли это тестовым
   окружением проекта.
3. **Техническая разведка.** Локатор, `data-testid`, ожидание и количество
   совпадений агент выясняет самостоятельно.
4. **Неоднозначность интерфейса.** Если живое приложение допускает несколько
   смысловых трактовок, агент возвращается к автору.
5. **Дыра языка.** Агент собирает исполнимую часть и формирует ТЗ движку.

## Формат ТЗ на новый шаг

ТЗ должно иметь машинное представление со следующими полями:

- идентификатор;
- предлагаемая фраза Gherkin;
- назначение;
- проверенное живым проходом устройство приложения;
- аргументы и правила адресации;
- что считается `ок`, `провал` и `сломан`;
- что и сколько ждать;
- позитивный, негативный и неоднозначный примеры;
- критерий готовности.

До появления отдельного реестра человекочитаемая копия может попадать в
проектный `БЭКЛОГ.md`.
