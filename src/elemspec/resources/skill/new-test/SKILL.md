# Агентский автор тестов elemspec

Работать только через MCP-сервер `elemspec`. Считать результат `get_contract`
единственным актуальным контрактом API и DSL.

## Жёсткие границы

- Выполнять операции над тестами только инструментами MCP `elemspec`.
- Не редактировать напрямую `tests/`, `src/`, `engine-gaps/` и `БЭКЛОГ.md`.
- Не использовать shell, `apply_patch`, встроенный browser или сторонний MCP
  для разведки, записи или запуска теста.
- Не генерировать одноразовый Playwright/Python/JavaScript-код.
- Исследовать интерфейс только через `browser_start`, `browser_action`
  и `browser_close` MCP `elemspec`.
- Не добавлять хост в `elemspec.toml` без явного решения пользователя.
- Не объявлять работу завершённой без результата `prove_test`.
- Не вставлять неизвестную фразу в feature. Недостающий шаг представлять
  комментарием `# ТЗ: engine-gap:<id>`.

Перед первым вызовом API прочитать [references/api.md](references/api.md).
При проектировании диалога или спорной классификации прочитать
[references/examples.md](references/examples.md).

## Машина состояний

Следовать состояниям по порядку:

`INTAKE → NEEDS_CLARIFICATION | READY_FOR_DISCOVERY → DISCOVERY →`
`LANGUAGE_GAP | DRAFT_READY → VALIDATED →`
`UNVERIFIED | APPLIED | BUG_FOUND → AWAITING_BUG_CONFIRMATION → APPLIED →`
`COMPLETE | COMPLETE_WITH_GAPS | BUG_CONFIRMED`.

Не имитировать переход текстом: каждый переход после `DRAFT_READY` подтверждать
структурированным ответом MCP `elemspec`.

## 1. Разобрать намерение

Из исходного текста на любом языке выделить:

- тестируемый URL;
- начальное состояние;
- действия пользователя;
- наблюдаемые ожидаемые результаты;
- данные и параметры.

Переводить только итоговый feature в русский DSL elemspec. Смысл и значения
сохранять на языке предметной области.

Задать вопрос только если отсутствует бизнес-решение: непонятно, что считается
успехом, какой объект выбрать или какое исходное состояние требуется.
Локатор, ожидание и устройство DOM выяснять самостоятельно.

Если hostname отсутствует в `разрешённые_хосты` контракта, остановиться и
попросить пользователя решить, относится ли он к тестовым окружениям проекта.

## 2. Исследовать приложение

Вызвать `browser_start` и сохранить `browser_session` и UUID `разведка`: только ядро
создаёт этот журнал evidence.

1. Открыть URL.
2. Получить `snapshot` через `browser_action`.
   Если точный текст уведомления или ошибки заранее неизвестен,
   вызвать `visible-text`, найти наблюдаемую фразу, а затем подтвердить её
   целевым `locator-check`. Не переносить в feature случайный текст всей страницы.
3. Выполнить нужный путь через `browser_action` с `click`, `hover`, `fill`,
   `select-html-option`, `select-value`, `read-value`, `key`.
   Для одиночного нативного HTML `<select>` использовать `select-html-option`
   с точной видимой подписью option. Не подменять это клавишами ArrowDown/Enter.
   Если автор явно разрешил любую из нескольких логических записей с одинаковым
   представлением, использовать отдельную операцию `select-any-value`.
   Для открытия записи списка использовать `table-row-open`, а для кнопки
   подтверждения — локатор `команда диалога`.
4. Для каждого элемента вызвать `browser_action` с `locator-pick`.
   Если требуемый элемент не попал в snapshot, но известен его уникальный
   локатор, вызвать `locator-resolve`: операция проверит ровно одно видимое
   совпадение и вернёт `ref` для дальнейших `click`, `fill`, `hover` и `read-value`.
5. Сохранить в черновике полученные доказательства:
   уникальность, число совпадений, выбранный вид локатора и долг.
   Для `navigation-item` с точной вложенной `label` использовать локатор
   `пункт навигации`, а не текст или сгенерированный CSS.
   Для `data-component="button"` с точной вложенной `label` использовать
   `команду`, а не технический `data-testid` или текст страницы.
   Для текстового `input`, `textarea` или `contenteditable` внутри именованного
   `data-testid` компонента выбирать `поле`, а не CSS путь к вложенному элементу.
   Для обычного HTML принимать сгенерированный CSS по стабильному `id`, `name`
   или `aria-label` без долга. `placeholder`, текст и произвольный CSS считать долгом.
6. Выполнить каждый клик и переход, который появится в feature.
   Отсутствие ожидаемого перехода не скрывать: это кандидат в реальный дефект.
7. Вызвать `browser_close` после завершения разведки.

Если действие фактически открыло или заменило форму, немедленно после него
добавить `Тогда открылась форма "<точный заголовок>"`. Если открылось
модальное окно — `Тогда открылся диалог "<точный заголовок>"`. Этот шаг ставить
до первого действия внутри нового окна. Точный заголовок подтвердить живым
`locator-pick` или `locator-check` вида `заголовок формы` / `заголовок диалога`.
Не добавлять эту проверку после действия, которое только раскрыло меню и не
открыло новую форму.

Для шага проверки значения поля вызвать `read-value` по подтверждённому `ref`.
Для шага `<лок> доступен/недоступен` вызвать `locator-check`: он возвращает
число `доступных` с учётом native `disabled` и `aria-disabled="true"`.
Очистку поля исследовать через `fill` с пустым значением.
Выбор значения из платформенного выпадающего списка исследовать одной операцией
`select-value` с `ref` именованного поля и точным `value`.
Выбор нативного HTML option исследовать `select-html-option`; в feature это
`я выбираю "<подпись>" в селектор "<CSS>"`. Не смешивать его с
платформенным `select-value`.
Операцию `select-any-value` использовать только для явного требования
`я выбираю любое значение ...`; она не является обходом неоднозначности строгого
шага.
Строку именованной таблицы проверять `table-row-check` с именем таблицы,
именем колонки и точным ожидаемым значением; не строить CSS по номеру строки.
Открывать такую строку операцией `table-row-open`. Команду внутри модального
`alertdialog` подтверждать через `locator-pick`: он обязан вернуть локатор
`команда диалога` без технического долга.

Не угадывать локаторы и не переносить их из похожего теста без живой проверки.

## 3. Собрать и проверить черновик

Сформировать в памяти `init.json` и `test.feature`.

- Использовать только фразы из `get_contract`.
- Проверять наблюдаемое требование, а не случайное текущее состояние.
- Выносить изменяемые данные и длинные CSS в `параметры`.
- Помечать текст/CSS-долг комментарием в feature.
- Разделять независимые пути на сценарии.

Вызвать `validate_draft`. При `INVALID` исправить диагностики и повторить.
При `LANGUAGE_GAP` подготовить по одному структурированному ТЗ на каждый
`engine-gap:<id>`.

## 4. Записать через рабочую сессию

1. Вызвать `start_session`.
2. Вызвать `prepare_draft` с валидированным черновиком и UUID `разведка`.
3. При `UNVERIFIED` вернуться в живую browser-сессию и собрать перечисленные
   недостающие доказательства.
4. При `BUG_FOUND` показать автору точные expected/actual и запросить
   подтверждение, что расхождение является дефектом приложения.
5. Для нового теста без расхождений принять автоматическую запись.
6. Для существующего показать пользователю точный `diff` и запросить явное
   подтверждение конкретной `ревизия_черновика`.
7. После подтверждения `BUG_FOUND` вызвать `apply_draft` с той же ревизией и
   `confirm_bug: true`.
8. Только после требуемого подтверждения вызывать `apply_draft`.
9. Для каждого `LANGUAGE_GAP` вызвать `register_engine_gap`.

Если исходник изменился после открытия сессии, не обходить конфликт: открыть
новую сессию и заново построить diff.

## 5. Доказать проверку

Вызвать `prove_test` только после применения теста и регистрации всех gaps.

- `COMPLETE`: весь исходный сценарий покрыт.
- `COMPLETE_WITH_GAPS`: исполнимая часть доказана, но часть требований ожидает
  реализации зарегистрированных gaps.
- `BUG_CONFIRMED`: исходный тест красный именно на подтверждённом автором
  расхождении и содержит снимок; искусственный red не требуется.
- Любой другой статус: работа не завершена; сообщить причину и следующий шаг.

Не выполнять собственную временную правку feature: `prove_test` мутирует только
изолированную копию и сохраняет отчёты.

## 6. Отчитаться

Кратко сообщить:

- что проверяет тест;
- итоговый статус;
- ссылки на созданные файлы теста;
- выбранные локаторы и технический долг;
- зарегистрированные engine gaps;
- результаты исходного green, red со снимком и финального green.

Не называть `COMPLETE_WITH_GAPS` полным покрытием.
Не называть `BUG_CONFIRMED` завершённым зелёным тестом: это зафиксированное
воспроизведение дефекта приложения.
